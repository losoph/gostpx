# Охват трафика: что ловится, что нет

Главный принцип проекта: **что можем перехватить — перехватываем, чего не
можем — честно показываем.** Никаких попыток дожать трафик, который
сопротивляется. Обоснование — [ADR-008](DECISIONS.md#adr-008).

Этот документ — не оговорка мелким шрифтом, а спецификация. То, что здесь
написано, обязано совпадать с тем, что показывает `gostpx status` и трей.

---

## Режим `tun`

### Ловится

- Весь **IPv4**-трафик всех процессов: TCP и UDP
- Консольные утилиты без каких-либо переменных окружения — `curl`, `git`,
  `ssh`, `brew`, `npm`
- Приложения с собственным сетевым стеком, игнорирующие системный прокси
- Игры, мессенджеры, всё, что ходит по raw-сокетам
- DNS — через локальный DoH-форвардер внутри туннеля

### Не ловится

| Что | Почему | Видно в статусе |
|---|---|---|
| **IPv6** | выключен по решению; TUN — только IPv4 default route | `IPv6: напрямую` |
| Трафик до самого прокси-сервера | физически необходимо, иначе петля маршрутизации | — |
| Локальная сеть | connected-маршруты более специфичны, чем default через TUN | — |
| mDNS, DHCP, broadcast | канальный уровень, ниже маршрутизации | — |
| Трафик чужого VPN | мы не трогаем его маршруты | `обнаружен другой VPN` |
| Приложения со встроенным своим туннелем | они не пользуются системной маршрутизацией | — |

### IPv6 — отдельно

Это самое заметное ограничение, и оно не про редкие случаи.

Если у сети есть рабочий IPv6, то dual-stack клиенты по RFC 6724 предпочитают
IPv6 при прочих равных. На практике это значит, что заметная доля трафика к
крупным площадкам — Google, YouTube, всё за Cloudflare — пойдёт **напрямую,
мимо прокси**, пока IPv6 поднят.

Способы это закрыть отвергнуты сознательно: отключать IPv6 на интерфейсе —
захват системы; заворачивать IPv6 в туннель — работа, выведенная из объёма.

Поэтому вместо обхода — индикация. При активной сессии тул проверяет наличие
рабочего IPv6 и, если он есть, показывает это в трее и в `status` как
предупреждение, а не прячет.

## Режим `sysproxy`

Работает без прав администратора, но ловит заметно меньше. На Windows —
меньше, чем на macOS.

Списки «Ловится» и «Не ловится» ниже — **ожидания** по документации платформ,
пока не подтверждены строкой в [COVERAGE-TESTS.md](COVERAGE-TESTS.md).
Подтверждённое вынесено в «Проверено руками». Ожидание может оказаться
неверным в обе стороны: например, Python `urllib` и Windows PowerShell 5.1
системный прокси читают, хотя запускаются из консоли.

### macOS

**Ловится:** Safari, Chrome, Edge, Firefox, приложения на CFNetwork
и NSURLSession — то есть большинство нативных GUI-программ.

**Не ловится:** консольные утилиты (`curl`, `git`, `ssh`, `npm` читают только
переменные окружения), приложения со своим сетевым стеком, UDP и QUIC, DNS.

### macOS — проверено руками

2026-09-25, v0.2.0-alpha.1 / 2026-09-27, v0.2.0-alpha.2, macOS 26.7 (Darwin 25.7.0, x86_64 Intel). Дефолт трея — 127.0.0.1:8080 / 1080 (замеры alpha.1 шли на стендовых портах 18080/11080):

- **Safari (M1):** проверено руками в v0.2.0-alpha.2 на стандартном порту 127.0.0.1:8080: https://ifconfig.me при «вкл» даёт IP прокси (192.0.2.10 RU), при «выкл» — реальный IP машины (203.0.113.30). Трафик Safari перехватывается.
- **Chrome / Edge (M2), Firefox (M3):** визуально глазами пока не проверялись, остаются ожиданиями.
- **Явный прокси (M13):** `curl -x http://127.0.0.1:18080 https://api.ipify.org` даёт IP прокси (198.51.100.20); прямой запрос без прокси — реальный IP машины.
- **Системный прокси:** `networksetup -getwebproxy Wi-Fi` и `-getsocksfirewallproxy Wi-Fi` корректно переключаются при старте сессии.
- **Откат при завершении (MR1, MR2):** и `gostpx off`, и `kill -TERM` снимают системный прокси с Wi-Fi до завершения процесса; в `state.json` пишется `user disabled` или `signal`.
- **Зависший прокси после сбоя (MR4):** после `kill -9` прокси остаётся на порту; при следующем запуске трей обнаруживает мёртвый PID, снимает прокси и выводит предупреждение `⚠ Снят зависший прокси (Wi-Fi)`.
- **Обрыв апстрима (MR6):** при обрыве TCP-релея движок фиксирует разрыв, системный прокси немедленно снимается, иконка в трее не меняет цвет (остаётся шаблонной чёрно-белой), а статус-текст меняется на «🔴 оборвано».
- **Главный поток UI (MR7):** в v0.2.0-alpha.2 главное меню не зависает при «Включить», подтверждено автоматическим смоук-тестом (5/5 итераций) и запуском из `/Applications`.

- **Соединения, открытые до включения (M15):** 2026-10-11, v0.2.0-alpha.8, macOS 26.7.1 x86_64 — ⚠ остаются прямыми, пока приложение само их не закроет. При автозапуске сторонний настольный клиент (Claude Desktop) стартовал на 12 с раньше трея и держал 3 прямых HTTP/2-соединения к своему API; новые соединения шли через прокси. Системный прокси действует только на новые соединения; переподключать чужие приложения тул не будет ([ADR-008](DECISIONS.md#adr-008)). Если важно — перезапустить приложение после «вкл».

### Windows

**Ловится:** Edge, Chrome и прочие потребители WinINET.

**Не ловится:** службы и приложения на WinHTTP, часть .NET-приложений,
всё со своим стеком, UDP и QUIC, DNS.

**Проверено руками** 2026-09-24, v0.1.0-alpha.3/alpha.4, Windows 11 (10.0.26200), SOCKS5-апстрим:

| Что | Результат |
|---|---|
| Браузер, ifconfig.me | IP прокси при `on`, реальный при `off` |
| Браузер, dnsleaktest.com | при `on` и `off` разные локации резолверов — имена резолвит прокси |
| `curl.exe https://ifconfig.me` без `-x` | ⚠ реальный IP: curl системный прокси не читает |
| Windows PowerShell 5.1 и PowerShell 7.6, `irm` | IP прокси — .NET читает настройки WinINET |
| Python 3, `urllib.request` | IP прокси — читает прокси из реестра |
| `curl.exe -x http://127.0.0.1:8080`, `--socks5-hostname 127.0.0.1:1080` | IP прокси |
| `off` | слушатели закрыты, WinINET снова напрямую |
| Edge, cloudflare-quic.com | HTTP/2: при системном прокси QUIC не используется, в обход не уходит |
| Telegram Desktop 7.2.9 | ⚠ без собственного прокси не работает — системный прокси ему не помогает |

**Опровергнутое ожидание:** «консоль не ловится» неверно — консольные
программы на .NET и Python системный прокси читают. Мимо идут программы
со своим сетевым стеком (`curl.exe`), а не консоль как таковая.

**Не измерено:** Firefox, WinHTTP, `git`, WebRTC, IPv6 — строки W3, W7,
W9, W11, W12, W15 в [COVERAGE-TESTS.md](COVERAGE-TESTS.md).

Отдельно: **SOCKS5 системный уровень Windows не поддерживает вовсе**. Поэтому
в этом режиме тул поднимает локальный HTTP-прокси, а уже он идёт в SOCKS5-апстрим.

### Локальные адреса

Запросы к `127.0.0.0/8`, `::1`, `localhost` и `*.localhost`, пришедшие в
слушатели, gostpx соединяет на этой машине напрямую, а не через апстрим
([ADR-019](DECISIONS.md#adr-019)): на прокси-сервере эти адреса означают
другую машину. Остальные имена и адреса, включая частные сети, идут через
апстрим как есть. Ключа в конфиге для этого нет.

### DNS в этом режиме

**Проксируемые соединения имя наружу не выпускают.** Слушатель получает
от приложения имя хоста и передаёт его апстриму как есть: SOCKS5 с
`ATYP=0x03`, HTTP `CONNECT host:port`, ssh — `DialContext` по имени.
Резолвит прокси-сервер. Тул локально не резолвит ничего
([ADR-009](DECISIONS.md#adr-009)).

Это не значит, что DNS в системе молчит:

- приложения, не уважающие системный прокси, резолвят сами и идут напрямую;
- браузеры со своим Secure DNS резолвят сами, мимо нас — мы это не трогаем
  принципиально ([ADR-008](DECISIONS.md#adr-008));
- некоторые приложения делают собственный lookup даже при настроенном
  прокси, например для проверки связи.

Настройка DoH в конфиге к режиму `sysproxy` **не применяется** — она про
режим `tun`. `gostpx status` это прямо говорит, а не делает вид, что
DoH работает.

## Чего тул не делает принципиально

Это не «пока не реализовано», а решение:

- **не блокирует QUIC и UDP/443**, чтобы заставить браузер откатиться на TCP;
- **не перехватывает DoH приложений** со своим резолвером — Firefox и Chrome
  с включённым Secure DNS продолжают резолвить сами, мимо нас;
- **не внедряется в процессы** и не подменяет их собственные настройки прокси;
- **не ставит локальный CA** и не расшифровывает TLS;
- **не трогает чужие VPN** и их маршруты;
- **не отключает IPv6** на сетевом интерфейсе;
- **не маршрутизирует по приложениям** — это задача Proxifier, и она прямо
  выведена из объёма проекта.

## Поведение при обрыве

Kill-switch отсутствует по решению. Значит:

**Если сессия обрывается, трафик идёт напрямую.** Без шифрования, к реальному
адресу назначения, с реальным IP. Молча этого не происходит: текстовый статус
в строке меню немедленно показывает `🔴 оборвано`, `gostpx status` показывает
`прямое подключение`, а причина обрыва пишется в лог (сама иконка трея —
монохромный шаблон macOS, адаптирующийся под светлую/тёмную тему). Определение
внешнего IP выполняется только по явному запросу (пункт «Принудительно обновить»
в меню с рейт-лимитом не чаще 1 раза в 10 сек, либо `gostpx status --check-ip`);
обычное открытие меню использует только кэш и не создаёт сетевого трафика.

Это и есть замена kill-switch в рамках принципа — не блокировать, а
не позволять ошибиться относительно текущего состояния.

**Автопереподключение и отказ локальной сети** ([ADR-018](DECISIONS.md#adr-018)).
Если пропала сама локальная сеть (нет интерфейса, маршрута по умолчанию,
ошибки «сеть недоступна»), сессия не снимается: статус `🟡 нет сети`,
трафику идти некуда ни через прокси, ни напрямую. Если отказал апстрим,
сессия обрывается как описано выше, но затем восстанавливается сама после
первой успешной проверки (паузы 5 → 10 → 20 → 40 → 60 с). Не
восстанавливается после ручного выключения, отказа в логине/пароле и
ошибки конфига. Пока идут попытки, статус — `🔴 оборвано — переподключение`
с номером попытки; всё это время трафик идёт напрямую.

При снятии или обрыве сессии системный прокси откатывается к состоянию до запуска: восстанавливается снимок настроек ([ADR-015](DECISIONS.md#adr-015)), если текущие настройки всё ещё указывают на порт gostpx; если настройки были изменены сторонней программой, они не затрагиваются.

### Зависший системный прокси и восстановление (R4)

Восстановление зависшего прокси при старте (`RecoverDanglingProxy` / сценарий R4): если процесс gostpx был аварийно завершён (`kill -9`, сбой питания), при следующем запуске проверяется доступность локального порта слушателя.
- Если порт свободен (никто не слушает), тул снимает оставшийся системный прокси и восстанавливает снимок.
- Если порт **занят любым процессом** (TCP-подключение успешно), тул осознанно **не снимает** системный прокси, соблюдая инвариант «чужой прокси не трогаем».
- Следствие: если на порту остался зависший сторонний процесс (не-gostpx listener) или сокет в полузависшем состоянии, системный прокси остаётся включённым — пользователю необходимо снять его вручную через системные настройки ОС.

Следствие, которое стоит держать в голове: **тул не годится для сценариев,
где утечка реального IP недопустима.** Он про удобное переключение, а не про
гарантию анонимности.

## Как это выражено в интерфейсе

`gostpx status` печатает охват, а не только факт подключения:

```
● подключено      socks5  proxy.example.net:8000   режим: tun
  охват           IPv4 TCP/UDP всех процессов, DNS через DoH
  ⚠ IPv6          активен в сети — идёт напрямую, мимо прокси
  внешний IP      203.0.113.7
```

```
● подключено      socks5  proxy.example.net:8000   режим: sysproxy
  охват           только приложения, уважающие системный прокси
  имена           резолвит апстрим, локально не резолвим
  ⚠ не в прокси   программы со своим стеком (curl, git), UDP/QUIC, чужие резолверы
  ⚠ DoH           не применяется в этом режиме
```

Строки с `⚠` — не ошибки, а честное описание. Они не должны исчезать
«чтобы не пугать».
