# Архитектура

## 1. Общая схема

Два процесса с разными привилегиями, разделённые IPC. Демон нужен только
режиму `tun` (Phase 3, отложено); в режиме `sysproxy` движок и слушатели работают
в UI-процессе (трей) или CLI (`gostpx on`), демон не устанавливается
([ADR-016](DECISIONS.md#adr-016)). Схема ниже показывает архитектуру обоих режимов.

```
 пользовательская сессия                    │  система
                                            │
┌───────────────────────────────────────┐   │
│  gostpx / gostpxw  (UI / CLI)         │   │
│                                       │   │
│  ├─ трей: статус, вкл/выкл, режим     │   │
│  ├─ окно настроек (Wails webview)     │   │
│  ├─ пароль: credentials.toml (0600)   │   │
│  ├─ sysproxy: движок, слушатели       │   │
│  │    net/http, SOCKS5, DirectDialer  │   │
│  │    (работает здесь, без демона)    │   │
│  └─ loopback напрямую (ADR-019)       │   │
└──────────────┬────────────────────────┘   │
               │ (только в Phase 3, tun)    │
     IPC: unix socket / named pipe          │
     JSON-RPC, ACL по UID/SID               │
               │                            │
┌──────────────▼────────────────────────────┴──────────────┐
│  gostpxd  (демон, root / LocalSystem; Phase 3, отложено) │
│                                                          │
│  ┌── ingress ──────────────┐   ┌── outbound ───────────┐ │
│  │ TUN  (utun / wintun)    │   │  proxy.Proxy          │ │
│  │ (только режим tun)      │──▶│   DirectDialer:       │ │
│  │                         │   │   socks5 / http / ssh │ │
│  └─────────────────────────┘   │                       │ │
│                                └───────────────────────┘ │
│  ┌── системный слой ────────────────────────────────────┐│
│  │ маршруты · DoH-форвардер · utun                      ││
│  │ watcher смены сети · pin-route до прокси-сервера     ││
│  └──────────────────────────────────────────────────────┘│
└──────────────────────────────────────────────────────────┘
```

## 2. Ключевая идея: один outbound, два ingress

Оба режима используют **один и тот же исходящий слой** — свой `DirectDialer`,
который говорит с апстримом напрямую и передаёт ему **имя хоста**, а не IP:

```go
type TargetDialer interface {
    DialTarget(ctx context.Context, host string, port int) (net.Conn, error)
    Close() error
}
```

Три протокола — `socks5`, `http`, `ssh` — реализованы в нём целиком
([ADR-010](DECISIONS.md#adr-010)). Сторонних ядер нет.

Меняется только то, откуда приходит трафик:

| Режим | Ingress | Привилегии | Что ловит |
|---|---|---|---|
| `tun` (Phase 3, отложено) | виртуальный интерфейс utun/wintun | root / admin | весь **IPv4**: TCP, UDP, QUIC, DNS, raw-сокеты |
| `sysproxy` | локальные слушатели HTTP CONNECT + SOCKS5 | нет | только приложения, уважающие системный прокси |

В режиме `sysproxy` движок работает непосредственно в процессе трея или CLI без демона ([ADR-016](DECISIONS.md#adr-016)):
- HTTP-слушатель построен на `net/http` и `httputil.ReverseProxy` для обычных `http://` запросов (с поддержкой сохранения соединений и корректным полузакрытием `CloseWrite`), а для HTTPS — методом `CONNECT` через hijack соединения;
- Запросы к loopback-адресам (`127.0.0.0/8`, `::1`, `localhost`, `*.localhost`) соединяются на машине напрямую, не уходя на апстрим ([ADR-019](DECISIONS.md#adr-019));
- Имя хоста передаётся апстриму как есть: резолвит сам прокси-сервер ([ADR-009](DECISIONS.md#adr-009)).

Переключение режима не трогает конфигурацию апстрима, а новый протокол
достаточно добавить в одном месте.

**Про DNS в двух режимах — механизмы разные, утечки нет ни в одном:**

- `sysproxy` — слушатель получает от приложения имя хоста и передаёт его
  апстриму как есть (SOCKS5 `ATYP=0x03`, HTTP `CONNECT host:port`,
  ssh `DialContext` по имени). Резолвит прокси-сервер
  ([ADR-009](DECISIONS.md#adr-009)).
- `tun` (Phase 3, отложено) — имени нет по природе L3, туда приходят пакеты с IP.
  Но DNS к этому моменту уже прошёл через локальный DoH-форвардер поверх прокси
  (§6), поэтому и здесь наружу мимо прокси ничего не уходит.

**Где здесь `tun2socks`.** В Phase 3 он планируется, но только как TUN-ingress
и gVisor-стек. Его протокольный слой не используется: `M.Metadata` содержит
только `DstIP`, и для прикладных слушателей это означало бы локальный резолв.
`proxy.Proxy` — интерфейс, поэтому он будет реализован поверх того же
`DirectDialer`, и «один outbound, два ingress» сохранится
([ADR-010](DECISIONS.md#adr-010)).

Точный охват каждого режима — что реально ловится, а что нет, — описан
в [LIMITATIONS.md](LIMITATIONS.md). Этот документ нормативный: статус в трее
и вывод `gostpx status` обязаны ему соответствовать.

## 3. Границы привилегий

Движок один (`internal/engine`), хостов у него два
([ADR-016](DECISIONS.md#adr-016), частично отменяет ADR-004):

| Режим | Где работает движок | Привилегии | Установка |
|---|---|---|---|
| `sysproxy` | UI-процесс (трей, `gostpx on`) | нет | не нужна |
| `tun` (Phase 3, отложено) | демон `gostpxd` | root / LocalSystem | явно, разовый пароль |

Одновременно активна не больше одной сессии: UI не запускает `sysproxy`
при активной `tun`-сессии демона, демон отклоняет `session.start` при
активной `sysproxy`-сессии пользователя.

Системный прокси (`sysproxy`) на обеих ОС пишет UI-процесс от имени
пользователя — на Windows это и так обязательно: настройки живут в `HKCU`,
а `LocalSystem` видит чужой куст.

Откат системного прокси (и на macOS, и на Windows) восстанавливает снимок настроек, снятый до включения, если текущие настройки всё ещё указывают на gostpx ([ADR-015](DECISIONS.md#adr-015)); если настройки изменены сторонней программой, они не затрагиваются.


## 4. Секреты не хранятся в демоне

Пароль прокси лежит в `credentials.toml` рядом с конфигом, права `0600`
([ADR-011](DECISIONS.md#adr-011)); системное хранилище не используется.
Демон его **не читает и не сохраняет на диск**: UI достаёт
креды при подключении и передаёт в составе команды `session.start` по IPC.
При остановке сессии демон обнуляет их в памяти.

`config.toml` пароля не содержит никогда.

## 5. IPC и его защита

Демон с правами root, слушающий сокет и умеющий подключаться к произвольному
хосту, — это потенциальный вектор повышения привилегий. Поэтому:

- **macOS**: unix-сокет в `/var/run/gostpx.sock`, права `0600`, доступ только
  для установившего пользователя. Дополнительно проверка UID пира через `LOCAL_PEERCRED`.
- **Windows**: named pipe `\\.\pipe\gostpx` с DACL, разрешающим доступ только
  SID установившего пользователя.
- Протокол — JSON-RPC, строго типизированные команды, никаких «выполни строку».
- Демон валидирует всё, что приходит: адреса, порты, пути. Конфиг демон читает
  из собственного root-owned файла, а не из пользовательского.

## 6. Две проблемы TUN-режима, которые надо решить явно

### 6.1 Петля маршрутизации

Как только TUN становится default route, трафик до самого прокси-сервера тоже
уходит в туннель — и всё встаёт. Решение: перед поднятием TUN демон добавляет
`/32` маршрут до IP прокси через **исходный** шлюз и держит его, пока сессия
активна.

Это не настройка и не bypass-лист, а физическая необходимость — в конфиге
такого ключа нет, демон ставит маршрут сам и снимает при отключении.

Осложнение: если прокси задан доменным именем, резолвить его надо **до**
включения туннеля, системным резолвером, и пинить все полученные адреса.

### 6.2 Смена сети и сон

Wi-Fi → Ethernet, смена SSID, выход из сна — всё это сбрасывает маршруты и меняет
default gateway. Старый bash-скрипт этот случай не переживает вовсе: он ставит
прокси на один сетевой сервис и забывает о нём.

Демон подписывается на события:
- macOS — `SCDynamicStore` на ключ `State:/Network/Global/IPv4`;
- Windows — `NotifyRouteChange2` / `NotifyIpInterfaceChange`.

По событию: пересчитать шлюз, переустановить pin-route до прокси, восстановить
default через TUN. В режиме `sysproxy` на macOS — переприменить настройки
к новому активному сетевому сервису.

### Чего здесь больше нет

Третьей проблемой был выбор схемы DNS. Он закрыт решением: всегда DoH, по
умолчанию `https://dns.google/dns-query`, адрес меняется в конфиге, CLI и GUI.
Демон поднимает локальный форвардер, TUN направляет в него порт 53, форвардер
резолвит по DoH через прокси. Вариант «UDP в туннель» отброшен — он требует
от апстрима `UDP ASSOCIATE`, которого у многих прокси нет.

В режиме `sysproxy` эта секция не применяется вовсе: имена резолвит сам
прокси-сервер. Тул обязан говорить об этом в статусе, а не делать вид, что
настройка DoH работает.

## 7. Честный статус вместо kill-switch

Kill-switch в проекте отсутствует по решению. При обрыве сессии трафик идёт
напрямую — и это **не скрывается**:

- иконка в трее немедленно становится красной;
- `gostpx status` показывает `прямое подключение` и причину;
- причина обрыва пишется в лог.

Это прямое следствие [ADR-008](DECISIONS.md#adr-008): не блокировать трафик,
а не позволять пользователю ошибиться относительно текущего состояния.

Инженерное требование, которое из этого вытекает: **переход в состояние
«оборвано» должен быть быстрым и не зависеть от опроса.** Индикация по
таймеру раз в минуту здесь не годится — падение сессии обязано приводить
к смене статуса немедленно, по событию из движка, а не по следующему
health-check.

Отдельно: демон пишет факт активной сессии в root-owned state-файл. При старте
он видит незакрытую сессию — значит, прошлый процесс умер аварийно, маршруты
могли остаться — и приводит систему в чистое состояние, сообщая об этом.

## 8. Статус и здоровье соединения

Старый скрипт раз в 5 секунд порождает `ping` и `curl` — это заметно для батареи
и всё равно показывает устаревшие данные. Вместо этого минимальная проверка:

- живость — дешёвый TCP-connect до прокси раз в 60 с, **в процессе**,
  без порождения процессов;
- задержка — измеряется на том же TCP-connect, без ICMP;
- внешний IP — **не опрашивается при старте трея**, только по явному действию пользователя (клик по меню трея показывает кэш или «—», кнопка «Обновить» опрашивает сеть не чаще раза в 10 с, либо `gostpx status --check-ip`), с кешем;
- обрыв сессии виден сразу по событию движка, не дожидаясь очередной проверки;
- в фоне интервал растягивается.

Отдельная проверка, специфичная для принципа честности: при активной сессии
в режиме `tun` демон выясняет, есть ли в сети рабочий IPv6, и если есть —
поднимает предупреждение в статусе, потому что этот трафик идёт мимо прокси
([LIMITATIONS.md](LIMITATIONS.md#ipv6--отдельно)).

## 9. Раскладка репозитория

```
cmd/gostpx/             трей-приложение на macOS (Wails v3) и CLI — единый бинарник
cmd/gostpxw/            GUI-приложение трея на Windows (Wails v3, WinGUI подсистема)
cmd/gostpxd/            системный демон (Phase 3, отложено)
internal/autostart/     управление автозапуском (LaunchAgent на macOS, Registry Run на Windows)
internal/cli/           разбор команд, вывод статуса, коды возврата, gostpx env
internal/config/        схема TOML, загрузка, валидация config.toml и credentials.toml (ADR-011)
internal/dns/           локальный DoH-форвардер (Phase 3, отложено)
internal/engine/        HTTP/SOCKS5 слушатели, outbound DirectDialer (socks5/http/ssh), reverse proxy, loopback bypass (ADR-019)
internal/ipc/           JSON-RPC транспорт и ACL для связи с демоном (Phase 3, отложено)
internal/netwatch/      отслеживание смены сети (Phase 3, отложено; базовый watcher в engine)
internal/notify/        системные уведомления об обрыве и восстановлении (macOS UserNotifications)
internal/session/       жизненный цикл сессии, probe loop, автопереподключение, обработка событий
internal/settings/      окно настроек (Wails v3 webview), точное сохранение TOML с сохранением комментариев
internal/state/         runtime-состояние активной сессии (state.json)
internal/sysproxy/      системный прокси: darwin.go (networksetup), windows.go (реестр HKCU + InternetSetOption), откат к снимку (ADR-015)
internal/testupstream/  тестовые заглушки апстримов для интеграционных тестов
internal/tun/           TUN-устройство, маршруты, pin-route (Phase 3, отложено)
build/                  упаковка (.app, .exe), смоук-тесты, CI
docs/                   документация проекта
```

Правило: `internal/engine` и всё под ним не знают ни про Wails, ни про UI.
Wails — тонкий слой сверху, заменимый без переписывания логики.

## 10. Три поверхности управления

Тул управляется тремя равноправными способами, и ни один из них не
привилегированный: **файл конфигурации**, **CLI** и **GUI**. Авторитетен файл
(ADR-007) — GUI и CLI поверх него равны в правах.

```
  config.toml ──┐
  (редактор)    │
                ├──▶ internal/config ──▶ internal/session (sysproxy)
  gostpx CLI ───┤         ▲              [Phase 3: IPC ──▶ gostpxd (tun)]
                │         │ fsnotify + валидация
  трей / окно ──┘         │ (ошибка → откат на старый конфиг)
```

Практическое следствие для разработки: любая новая настройка попадает
одновременно в схему TOML, в CLI и в GUI. Это дороже одной поверхности, но
делает тул скриптуемым и независимым от судьбы Wails.

Второе следствие — порядок работ. Конфиг и CLI строятся первыми, трей
подключается к готовому ядру. См. [ROADMAP.md](ROADMAP.md).

Подробности: [CONFIG.md](CONFIG.md) и [CLI.md](CLI.md).
